### 问题现象

```mysql
CREATE TABLE SchRSolutionRosterWarning (
    id INT PRIMARY KEY AUTO_INCREMENT,
    task_id INT NOT NULL,
    person_id INT NOT NULL,
    task_date DATE NOT NULL,
    solution_id INT NOT NULL
);

INSERT INTO SchRSolutionRosterWarning (task_id, person_id, task_date, solution_id) VALUES
(1, 101, '2025-07-01', 100),  -- 记录A：被事务1的taskIds和事务2的personIds命中
(2, 102, '2025-07-02', 100);  -- 记录B：被事务1的personIds和事务2的taskIds命中

```

### 模拟并发事务

假设有两个并发事务（事务1和事务2），执行顺序如下：

|时间线|事务1|事务2|
|---|---|---|
|**t1**|`DELETE WHERE task_id IN (1)`  <br>（锁定**记录A**）||
|**t2**||`DELETE WHERE task_id IN (2)`  <br>（锁定**记录B**）|
|**t3**|`DELETE WHERE person_id IN (102)`  <br>（尝试锁定**记录B**，等待事务2释放）||
|**t4**||`DELETE WHERE person_id IN (101)`  <br>（尝试锁定**记录A**，等待事务1释放）|
|**结果**|⚠️ 死锁发生！|⚠️ 死锁发生！|

---

### **关键点解析**

1. **循环等待条件**：
    
    - 事务1持有**记录A**的锁，请求**记录B**的锁
        
    - 事务2持有**记录B**的锁，请求**记录A**的锁
        
2. **代码触发路径**：
    
    - 事务1：`taskIds = [1]` → `personIds = [102]`
        
    - 事务2：`taskIds = [2]` → `personIds = [101]`
        
3. **锁机制**：
    
    - `DELETE`语句会获取行的**排他锁（X锁）**
        
    - 当两个事务以相反顺序访问相同行时，形成死锁环路


### **解决方案建议**

破掉循环，查的时候不会加锁，delete的时候排队等待。

```java
// 如果在事务中，就不去用线程池去读了，会读不到未提交的

        LambdaQueryWrapper<SchRSolutionRosterWarning> queryWrapper = new QueryWrapper<SchRSolutionRosterWarning>().lambda()  
                .in(SchRSolutionRosterWarning::getTaskId, list)  
                .eq(SchRSolutionRosterWarning::getSolutionId, SolutionIdHolder.threadLocal.get())

        warningIds.addAll(baseMapper.selectList(queryWrapper).stream().map(SchRSolutionRosterWarning::getId).collect(Collectors.toSet()));  
    });  
  
}  
if (CollectionUtils.isNotEmpty(personIds)) {  
    List<Collection<String>> splitList = MathUtil.batchList(personIds, 2000);  
    splitList.parallelStream().forEach(list -> {  
        LambdaQueryWrapper<SchRSolutionRosterWarning> queryWrapper = new QueryWrapper<SchRSolutionRosterWarning>().lambda()  
                .in(SchRSolutionRosterWarning::getPersonId, list)  
                .eq(SchRSolutionRosterWarning::getSolutionId, SolutionIdHolder.threadLocal.get())  
                .eq(SchRSolutionRosterWarning::getModuleFlag, ModuleFlagHolder.threadLocal.get())  
                .ge(SchRSolutionRosterWarning::getTaskDate, startDate)  
                .in(CollUtil.isNotEmpty(ruleIdList), SchRSolutionRosterWarning::getRuleId, ruleIdList);  
        queryWrapper.select(SchRSolutionRosterWarning::getId);  
        warningIds.addAll(baseMapper.selectList(queryWrapper).stream().map(SchRSolutionRosterWarning::getId).collect(Collectors.toSet()));  
    });  
}  
if (CollUtil.isNotEmpty(warningIds)) {  
    List<Collection<String>> splitList = MathUtil.batchList(warningIds, 5000);  
    splitList.parallelStream().forEach(list -> {  
        baseMapper.deleteBatchIds(list);  
    });
```

```java
if (CollectionUtils.isNotEmpty(taskIds) || CollectionUtils.isNotEmpty(personIds)) {
    baseMapper.delete(new QueryWrapper<SchRSolutionRosterWarning>().lambda()
        .and(wrapper -> {
            if (CollectionUtils.isNotEmpty(taskIds)) {
                wrapper.in(SchRSolutionRosterWarning::getTaskId, taskIds);
            }
            if (CollectionUtils.isNotEmpty(personIds)) {
                wrapper.or().in(SchRSolutionRosterWarning::getPersonId, personIds)
                       .ge(SchRSolutionRosterWarning::getTaskDate, startDate);
            }
        })
        .eq(SchRSolutionRosterWarning::getSolutionId, SolutionIdHolder.threadLocal.get())
```
