# MysqlRR级别幻读解决方案解析 SQL优化技术

InnoDB 在 **RR（Repeatable Read）** 隔离级别下，主要通过 **MVCC（多版本并发控制）** 和 **Next-Key Locking（临键锁）** 解决了 **大部分常见的幻读问题**，但并非所有场景。具体来说，它解决了以下场景的幻读：  

---

### **1. 纯快照读（非锁定读）场景下的幻读**
**场景**：  
- 事务 A 执行 `SELECT * FROM t WHERE id > 100`（普通查询，不加锁）  
- 事务 B 插入 `id = 101` 并提交  
- 事务 A 再次执行相同的 `SELECT`  

**InnoDB 的解决方案**：  
- 通过 **MVCC**，事务 A 的两次查询会基于 **同一快照**，因此不会看到事务 B 新插入的行，避免了幻读。  

**结论**：**纯 `SELECT` 查询不会出现幻读**。  

---

### **2. 锁定读（当前读）场景下的幻读**
**场景**：  
- 事务 A 执行 `SELECT * FROM t WHERE id > 100 FOR UPDATE`（加锁读）  
- 事务 B 尝试插入 `id = 101`  

**InnoDB 的解决方案**：  
- 使用 **Next-Key Locking**（临键锁），锁定 `id > 100` 的索引记录及其间隙，阻止事务 B 插入 `id = 101`，从而避免幻读。  

**结论**：**`SELECT ... FOR UPDATE` 或 `SELECT ... LOCK IN SHARE MODE` 可以防止幻读**。  

---

### **3. 连续两次当前读的场景**
**场景**：  
- 事务 A 执行 `SELECT * FROM t WHERE id > 100 FOR UPDATE`  
- 事务 B 尝试插入 `id = 101`（被阻塞）  
- 事务 A 再次执行相同的 `SELECT ... FOR UPDATE`  

**InnoDB 的解决方案**：  
- 由于临键锁的存在，事务 B 无法插入数据，事务 A 的两次查询结果一致，不会出现幻读。  

**结论**：**连续锁定读不会出现幻读**。  

---

### **🔴 未解决的幻读场景（例外情况）**
InnoDB 的 RR 隔离级别 **并非完全解决所有幻读**，在以下情况仍可能出现幻读：  

#### **情况 1：先快照读，后当前读**
```sql
-- 事务 A
SELECT * FROM t WHERE id > 100;          -- 快照读，看不到新数据（无幻读）
SELECT * FROM t WHERE id > 100 FOR UPDATE; -- 当前读，可能看到新插入的数据（幻读）
```
- 第一次查询是 **快照读**（MVCC），第二次是 **当前读**（临键锁），如果事务 B 在两次查询之间插入了数据，第二次查询可能会看到新数据，导致幻读。  

#### **情况 2：先查询后更新**
```sql
-- 事务 A
SELECT * FROM t WHERE id > 100;          -- 快照读，看不到新数据
-- 事务 B 插入 id=101 并提交
UPDATE t SET name='new' WHERE id > 100;  -- 更新会作用到新插入的行
SELECT * FROM t WHERE id > 100;          -- 现在能看到 id=101（幻读）
```
- 虽然第一次 `SELECT` 是快照读，但 `UPDATE` 会基于 **最新数据** 执行，可能修改其他事务新插入的行，导致后续查询出现幻读。  

---

### **📌 总结**
| 场景 | 是否解决幻读 | 原因 |
|------|------------|------|
| **纯快照读（普通 `SELECT`）** | ✅ 解决 | MVCC 保证一致性视图 |
| **锁定读（`SELECT ... FOR UPDATE`）** | ✅ 解决 | Next-Key Locking 阻止插入 |
| **连续锁定读** | ✅ 解决 | 临键锁持续生效 |
| **先快照读后当前读** | ❌ 未解决 | 两次查询模式不同 |
| **先查询后更新** | ❌ 未解决 | `UPDATE` 基于最新数据 |

**结论**：  
- InnoDB 在 RR 级别下 **解决了大部分幻读问题**，尤其是纯查询和锁定读场景。  
- 但在 **混合使用快照读和当前读** 或 **先查询后更新** 时，仍可能出现幻读。  
- 如果业务要求 **完全避免幻读**，可以使用 **Serializable（串行化）** 隔离级别，或合理使用 `SELECT ... FOR UPDATE` 进行锁定。
